# Ravelin

A 3D racer where you never steer. The car drives itself, forward, always. You lay the
track ahead of it, piece by piece, from a hand of parts, while it closes the distance.

Full design in [design/](design/) — read `01-core-loop.md` first.

## Golden rule of this codebase

**Every rule of the game lives in `Packages/RavelinCore`, which has zero Apple imports and
builds and tests on Linux. The RealityKit layer in `App/` renders a snapshot and decides
nothing.**

Development happens on Linux; only building and running happen on macOS. If a piece of
logic cannot be tested with `make test` on Linux, it is in the wrong place.

## Determinism is not optional

- The simulation runs on `Fixed` (Q32.32 fixed-point), never `Double`. Float results
  differ between x86-64 and ARM64, and a replay recorded on the Linux dev box must
  reproduce bit-exactly on an iPhone.
- Trigonometry comes from `Trig` (CORDIC, project-owned table), never from `libm`.
- The arctan table and CORDIC gain are generated, not hand-written. If they ever need
  regenerating:
  `python3 -c "import math; print([round(math.atan(2.0**-i)*2**32) for i in range(32)])"`
- `DeterminismTests` holds golden fingerprints. **If one fails, the simulation changed.**
  Do not update a golden value without understanding why it moved.
- Fixed-step integration at 1/120 s. The renderer interpolates; it never advances the sim.
- One `SplitMix64` stream per session, with sub-streams derived by purpose so adding a new
  random consumer does not shift existing rolls.

## Environment

### Linux (development)

Swift 6.3.3 via swiftly. Ubuntu 26.04 is not a recognised swiftly platform, so it was
installed with `--platform ubuntu24.04`, and the 24.04 toolchain needs two libraries that
26.04 no longer ships. They live in `~/.local/share/swiftly/compat-libs` and are picked up
via `LD_LIBRARY_PATH` — the Makefile does this automatically:

- `libxml2.so.2` (26.04 has `.so.16`)
- `libicu*.so.74` (26.04 has a newer ICU)

Both were extracted from Ubuntu 24.04 debs into a user directory. Nothing was installed
system-wide and no sudo was used.

`make doctor` checks the setup.

### macOS (building and running)

Xcode 16+, `brew install xcodegen`. `.xcodeproj` is generated by `make gen` and is **not**
committed — regenerate it after pulling. No compat libraries are needed; the Makefile only
adds them on Linux.

### The first Mac run — what it is actually for

There is **no iOS app yet**; the RealityKit layer starts at Milestone 6. The reason to run
this on a Mac now is to prove the simulation is architecture-independent:

```
swift --version          # expect Swift 6.x, arm64-apple-macosx
make test                # expect 80 tests, 0 failures
```

The suite that matters is `DeterminismTests`. These three fingerprints were computed on
x86-64 Linux and are asserted, not recomputed:

| Test | Expected |
|---|---|
| `testTransformChainMatchesGoldenFingerprint` | `17638089423717976749` |
| `testCatalogGeometryMatchesGoldenFingerprint` | `13396143040586426581` |
| `testFixedArithmeticGoldenVector` | `9673759134698064605` |
| `testReplayMatchesGoldenFingerprint` | `14728847889759036489` |

If they pass on ARM64, replays, ghosts and stored level solutions are portable between
the two machines, which is the entire reason the simulation uses `Fixed` and CORDIC rather
than `Double` and `libm`.

**If one fails, do not update the constant.** It means a floating-point path or a
platform-dependent library call leaked into the simulation. Find it and remove it.

## Code style

No comments. None — not doc comments, not explanatory `//`, not TODOs. Names carry the
meaning. This is a hard project rule.

## Geometry model — read before touching Track/

- A piece is a list of **constant-curvature segments**, not a baked exit transform. The
  exit frame comes from integrating the same ribbon the car drives on, so the visible
  surface and the collision surface cannot diverge.
- **Yaw defaults to `.world`.** Turning about the body axis does not preserve gradient —
  a 120° hairpin taken at a 12° climb comes out descending. Real track turns about the
  world vertical; surface bank is a separate roll. `.body` exists for Magnetite, where
  the track is genuinely rolled onto walls and ceilings.
- **Geometry is integrated in world space at placement time**, never cached per piece
  type. A cached local frame has its own idea of "up", which breaks world-axis yaw the
  moment the piece is placed on a graded track. `PieceGeometry.samples(from:)` takes the
  entry frame; `TrackChain` stores the resulting world samples per placed piece.
- Positive pitch is **nose up**. The Euler constructor negates it against the raw
  right-handed rotation about X.

## Known gap: archetype balance

`RavelinCLI sweep` re-solves every level under each deck archetype's palette. Most
archetype/world combinations currently fail, because intersecting a 12-slot archetype deck
with a 12-piece world palette leaves too few pieces to route with. The 60 stored solutions
are verified and shipping-safe; what is not yet true is that every archetype can beat every
world. Fixing it means widening world palettes, narrowing archetypes, or both — do it with
the sweep in front of you, not by intuition.

## Levels are generated route-first

Generating gates and then searching for a path produced mostly unsolvable levels. The
pipeline is inverted: `RouteWalker` random-walks a route that is drivable by construction
(speed, grip and clearance checked per piece), then the gates and cores are placed **on
that route**. `Solver` afterwards looks for a shorter line to set par. A level whose
solution does not survive the real physics is not written out.

Regenerate with `RavelinCLI solve`, which rewrites `Level/LevelSolutions.swift`.

## The estimator must not lie to itself

`SpeedEstimator` approves candidate pieces for the walker and the solver. Two mistakes
cost a lot of time here:

- `worstExcess` started at zero, so it could never report a *negative* excess, and every
  safety margin below zero rejected the entire catalog.
- The estimator clamped speed to a floor instead of reporting a stall, so it happily
  approved climbs the car cannot make. Pitch accumulates across pieces, so two steep rises
  in a row is a 60° wall where gravity beats the engine and the car stops dead. The
  estimator now reports `stalled` and `steepestGrade`, and `Physics` crashes a car that
  sits under half a metre per second for four seconds rather than freezing forever.

## Self-intersection is an arc-length question

Ribbon capsules are wide (radius = half the track width plus a margin), so any two pieces
laid consecutively overlap geometrically. That is not a collision, it is a join. The real
question is whether the track returns to a place it has already been **after travelling a
meaningful distance along itself**, so `ClearanceIndex` ignores anything within
`selfContactWindow` (20 m) of the candidate's own arc range. The window has to sit between
two bounds: above the widest combined capsule radius (17 m for two wide plates) and below
the tightest possible self-return (42 m, a circle of hairpins).

## Physics calibration

`Physics.corneringGrip` is an explicit arcade constant, currently 6. Real tyre grip makes
this catalog unplayable: a Sharp Curve is a 11.5 m radius, which at 30 m/s demands 8 g.
The constant states the arcade choice out loud instead of hiding it in a fudged mass or
gravity. Milestone 5 retunes it against the archetype sweeps; until then, changing it
moves every cornering test at once, which is the intended blast radius.

Bank is measured from the ribbon frame, not accumulated per piece. A Bank piece must still
be helping when the following curve arrives — that carry-over is the mechanic.
